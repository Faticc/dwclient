# dwclient

Безоконный клиент Minecraft 1.7.10 для компьютера OpenComputers. Заходит на сервер как
обычный игрок, показывает чат в окне и отправляет сообщения и команды. Рассчитан на
[DwOS](https://github.com/Faticc/dwos), работает и на OpenOS.

Нужны интернет-карта (хватит первого уровня) и, желательно, карта данных — она даёт
настоящую случайность вместо самодельной. Памяти нужно **от 384 КБ**: на 192 КБ не
влезает, там сама система оставляет свободными около пяти килобайт.

## Установка

На компьютере с OpenOS или DwOS и интернет-картой:

```
wget -f https://raw.githubusercontent.com/Faticc/dwclient/main/install.lua /tmp/i.lua && /tmp/i.lua
```

Клиент ляжет в `/home/dwclient`. Дальше остаётся вписать идентификатор сессии в
`session.lua` -- это единственный файл под правку руками:

```lua
return {
    username = "Buyanov",
    uuid = "e4861d55-588d-36d7-9f8b-777e46d60087",
    access_token = "",   -- вот сюда
}
```

Ник и uuid уже проставлены. uuid не выдуман: сервер в офлайн-режиме считает его как UUID
версии 3 от строки `"OfflinePlayer:<ник>"` -- формула проверена на известном значении.
Меняешь ник -- пересчитай и uuid.

Запуск — `/home/dwclient/main.lua`. Печатать можно сразу, Enter отправляет строку в чат.
Ctrl+Alt+C закрывает соединение по-человечески, а не убивает программу на середине
пакета (на DwOS; OpenOS такого не умеет).

## Обновление

```
/home/dwclient/update.lua
```

Это тот же самый `install.lua`, только уже лежащий рядом с клиентом. Качается лишь то,
что отличается: у каждого файла в `manifest.lua` записаны размер и CRC32, скачанное
сначала ложится в `.part` и подменяет старое, только если сошлось. Оборванная загрузка
рабочий клиент не портит. `session.lua` и `hwid.lua` обновление не трогает -- вписанное там переживёт любое
количество запусков `update.lua`.

Ключи у обоих одинаковые: `--repo=владелец/репо`, `--branch=ветка`, `--dir=подкаталог`,
`--to=/путь`, `--dry` (только показать, что изменится), `--force`.

## Что где лежит

```
install.lua   установщик, он же обновлялка (запускается под OpenOS/DwOS)
src/          исходники с комментариями и проверками
dist/         то же без комментариев + manifest.lua — это качает установщик
tools/        сборщик
```

Внутри `src/`:

```
main.lua        точка входа: окно, клавиатура, цикл пакетов
session.lua     кто заходит — единственный файл под правку руками
hwid.lua        описание машины, которое уходит в Login Start
auth.lua        обращение к серверу сессий (join)
connection.lua  вход, шифрование, игровой цикл
fml.lua         рукопожатие Forge
ui.lua          окно чата
modlist.lua     164 мода пака, снято прямо с jar'ов
channels.lua    ~130 каналов, оттуда же
```

`hwid.lua` описывает выдуманную машину, выведенную из строки-семени, а не чей-то
настоящий компьютер. Если бот не один, каждому стоит сделать свой — иначе все они
выглядят одной машиной.

## Сборка

```
python tools/build.py --src src --out dist
```

Сборщик лексером Lua снимает с кода комментарии, отступы и пробелы между знаками (строки
и длинные скобки не трогает), пишет `dist/` и `manifest.lua` с размером и CRC32 каждого
файла. Ужатое сверяется с исходником по байткоду `luac -s`: если программа стала хоть
чем-то другой, сборка не проходит. Выходит 119 КБ → 73 КБ, минус 39%.

Лексер и формат манифеста взяты у DwOS (`tools/dwosbuild.py`), чтобы установщик и
обновлялка вели себя ровно так же.

## Почему вход быстрый, хотя AES на чистом Lua

Тела пакетов, которые клиенту не нужны, **не расшифровываются вовсе**. Это не догадка,
а следствие устройства CFB8: при расшифровке в регистр вдвигается входной байт, то есть
сам шифротекст, а ключевой поток нужен только чтобы получить открытый текст. Значит по
ненужному куску можно просто прокрутить регистр -- без единого блока AES -- и остаться
ровно в том же состоянии.

Считается только начало каждого пакета (96 байт): этого хватает на id, имя канала и
первый байт содержимого. Рукопожатию FML большего и не надо -- ему нужен один
дискриминатор. Поэтому реестр блоков и предметов на 45 КБ, который клиент всё равно не
читает, стоит теперь ноль вместо 45 тысяч блоков AES.

`test_cfb8.lua` проверяет сам пропуск на шестнадцати сочетаниях размеров, а
`test_skip_flow.lua` -- что после него поток не сбит: там настоящий по формату сервер,
реестр в 45 КБ и чат следом, который обязан прочитаться верно.

## Почему RSA перестала быть узким местом

Модульное возведение в степень с e=65537 -- это всего ~18 умножений по модулю, но
взятие остатка делалось двоичным делением: сдвиг и вычитание, O(бит) проходов, на
каждом работа со всеми разрядами. Для модуля в 1024 бита это порядка двух тысяч проходов
по 64 разрядам против 64*64 = 4096 действий на само умножение. Одно приведение стоило
как тридцать умножений -- деление и было всем временем RSA.

Теперь приведение по Барретту: одно дорогое деление на подготовку (mu = b^(2k)/m) и
дальше два умножения вместо каждого деления. Замер на обычном Lua:

```
1024 бит: было 1.259 с, стало 0.090 с -- в 14 раз
2048 бит: было 4.699 с, стало 0.313 с -- в 15 раз
```

Ответ при этом тот же -- это проверяется, а не предполагается: `test_bignum.lua` сверяет
Барретта с честным делением на случайных числах четырёх размеров и на краях (0, m-1, m,
m^2-1). Ошибка в поправке частного не упала бы, а тихо дала бы неверный шифротекст, на
который сервер ответил бы невнятным отказом.

Дальше ускорять RSA особого смысла нет: она стала дешевле всего остального. И нет,
картой данных её не ускорить -- там AES, SHA-256, MD5, deflate и ECDSA на третьем
уровне, модульного возведения в степень нет вовсе.

## Что клиент рассказывает о себе

Тяжёлое здесь считается на самой машине -- RSA при входе и AES побайтово на каждом
пакете, -- поэтому "висит" и "работает" со стороны неотличимы. Клиент говорит вслух, что
делает:

```
  0.0s        открываю сокет на proxy-1.metalabsmc.net:25606
  0.3s +0.3   Login Start ушёл (571 Б: локаль + ник + 8 полей)
  1.1s +0.8   пришёл Encryption Request
  1.1s        ключ сервера разобран (1024 бит)
  9.4s +8.3   секрет зашифрован -- 8.3 с
 17.6s +8.2   маркер зашифрован -- 8.2 с
 17.7s        Encryption Response ушёл, шифрование включено
 18.9s +1.2   вошёл; собираю рукопожатие FML
 19.0s        FML: объявил каналы (1492 Б) и 164 мода (3722 Б)
 41.2s +22.2  расшифровано 45486 Б -- 22.2 с
 41.3s        FML: получил реестр блоков и предметов
 41.9s +0.6   FML: рукопожатие завершено
 42.1s +0.2   Join Game: сервер впустил в мир
```

Слева -- секунды от запуска, `+` -- сколько занял сам шаг. Долгие шаги показывают себя
ещё и в строке состояния, пока идут: `расшифровка 45486 Б: 40% (18194 из 45486 Б, 9 с)`.
В игре там же видно, живо ли соединение: `пакетов 312, последний 0x3F (1874 Б)`.

Строка состояния переписывается на месте, а вехи ложатся в чат, так что экран не
засоряется. Прогресс обновляется не чаще раза в пару секунд -- ровно тогда, когда
считающий код и так уступает управление, то есть бесплатно.

Цифры выше -- пример раскладки, а не замер: сколько именно займёт RSA и расшифровка на
вашей машине, покажет первый же запуск, и именно это теперь видно.

## Проверки

Все запускаются на обычном Lua, без Minecraft:

```
lua src/test_login_bytes.lua    логин собирается побайтово так же, как в питоновском клиенте
lua src/test_skip_flow.lua      пропуск тел не сбивает поток шифрования
lua src/test_ui_ocvm.lua        окно на эмулированной машине DwOS + счётчики вызовов
lua src/test_install_ocvm.lua   ставит клиент в /home/dwclient и запускает его из /home
lua src/test_yield_ocvm.lua     проверяет, что уступка управления настоящая
lua src/test_sha1.lua  src/test_aes.lua  src/test_cfb8.lua  src/test_rsa.lua
lua src/test_server_hash.lua    хеш сервера, включая java-шную двоичную дополняющую форму
```

`test_ui_ocvm.lua` берёт эмулятор машины OpenComputers из репозитория DwOS; путь к нему
передаётся доводом или переменной `DWREPO`.

## Про графику

Прямой вызов к видеокарте стоит долю бюджета тика, вызов в буфер видеопамяти — нет.
Поэтому чат рисуется в холст `gfx.surface`, а на экран кадр уходит не чаще раза в тик.
Замерено на эмуляторе, 40 цветных строк:

```
через буфер   screen=362  buffer=438  bitblt=2
напрямую      screen=671  buffer=0    bitblt=0   → в 1.9 раза меньше вызовов к экрану
```

Почти всю разницу даёт именно ограничение «не чаще кадра в тик». Ранняя версия
показывала кадр после каждого сообщения и набирала 996 вызовов — **хуже**, чем прямая
отрисовка. Буфер, который слишком часто выталкивают на экран, не оптимизация.
